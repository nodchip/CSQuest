# NC-Applications の対応状況

出典: [CS2023, NC-Applications](https://ieeecs-media.computer.org/media/education/reports/CS2023.pdf) 印字 p. 199。原典を要約した作業用一覧。依頼62は固定された簡略モデルであり、実際の通信やアプリケーションの実装ではない。

## トピック

| 番号 | 分類 | 要約 | 現状 |
|---:|---|---|---|
| 1 | CS Core | DNS や URI などの名前と住所 | 依頼421で架空の名前の問い合わせとキャッシュの期限を操作。URI、別名、失敗、実際の解決と一般的な名前付けは未対応 |
| 2 | CS Core | クライアント・サーバー、P2P、クラウドなど | 依頼62で端末がサーバーへ依頼する例。方式の比較は未対応 |
| 3 | CS Core | 遅延・帯域・損失耐性などアプリケーションの要求 | 応答消失の一例のみ。一般的な要求の分析は未対応 |
| 4 | CS Core | HTTP などのアプリケーション層プロトコル | 依頼62で POST と再送、425で HTTPS の GET と証明確認の固定例。HTTP 全体や実通信は未対応 |
| 5 | CS Core | TCP・UDP・ソケット API との相互作用 | 依頼424で TCP の接続開始の固定例。UDP、ソケット API と実際のアプリケーションは未対応 |

## 学習成果

| 番号 | 分類 | 要約 | 現状と限界 |
|---:|---|---|---|
| 1 | CS Core | 名前、住所、資源の位置の原則を定義 | 依頼421で名前から IPv4 住所を得る固定模型。一般の資源の位置や自由な説明は未対応 |
| 2 | CS Core | ネットワークアプリの要求を分析 | 未着手 |
| 3 | CS Core | アプリケーション層プロトコルの詳細を説明 | POST 再送の一例のみ。プロトコルの詳細や自由な説明は未対応 |
| 4 | CS Core | 単純なクライアント・サーバーのソケットアプリを実装 | 未着手。ゲーム操作は実装能力を評価しない |

依頼62は、最初の処理が成功し返事だけが失われる状況をプレイヤーに明示する。HTTP が自動的に重複を抑えるわけではなく、識別番号に対応するサーバーを仮定した例である。

依頼421は架空の `library.example` と文書用住所 `192.0.2.42`、４刻の TTL を使う。最初と期限後はルート・TLD・権威サーバーを順に訪れ、期限内は保存した住所を返す。[RFC 1034](https://www.rfc-editor.org/rfc/rfc1034) と [ICANN の説明](https://www.icann.org/en/rssac/faq)を参照。実際には委任情報も保存され、期限切れデータを例外的に使用できる場合もあるため、毎回同じ経路になるとは限らない。

依頼425は [RFC 9110 の HTTPS の証明確認](https://www.rfc-editor.org/rfc/rfc9110#section-4.3.4) を参考に、DNS・TCP・証明・HTTP を固定模型として結ぶ。証明の期限と秘密鍵の保有確認は与件とし、対象名や信頼関係の不一致では送信前に中止する。実通信・暗号計算や HTTP/3 の接続処理は扱わない。
