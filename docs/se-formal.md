依頼242は精霊Ａ・Ｂが各自「外、確認後、部屋の中、退出済み」を順に一度だけ進む有限模型。相手が部屋にいる間は外から確認後へ進めない。「別々」では確認後に再確認せず入室でき、Ａ確認・Ｂ確認・Ａ入室・Ｂ入室が同時入室の反例となる。「一つにする」では入室時にも相手がいないことを原子的に確認するため、到達可能状態に同時入室はない。探索は安全性のみを扱い、実装の正しさ、無限の動き、公平性や進行性は証明しない。

依頼242の手数を限った探索は、初期状態からの合法な行動順を列挙し、同時入室を満たすものを探す。別々の確認では上限３手まで見つからず、４手で反例が見つかる。[Alloy の模型探索の説明](https://alloytools.org/faq/what_kind_of_analysis_does_the_alloy_analyzer_do.html)を参考にするが、実際の Alloy や SAT ソルバーは使わない。上限内の不在は、長い手順や別の模型の安全性を示さない。

同じ探索では「入口を封鎖」を選び、同時入室と一人以上の入室を別々に探せる。封鎖では確認後から先へ進めないため同時入室を防ぐが、誰も入室できない。入室可能な行動順の存在も、すべての行動順でいつか入室することを保証しない。安全性と進行性の区別は [Lamport の解説](https://lamport.azurewebsites.net/tla/safety-liveness.pdf)を参照し、この有限例では無限の実行や公平性の証明は扱わない。

依頼243は在庫と依頼数を０〜３に限る16組について、正常・数不正・在庫不足の結果と残数を契約に照らして比較する。「在庫３・依頼１」の一件は４通りの規則ですべて成功するが、０の拒否や在庫と同数の許可に欠陥がある規則は他の入力で反例が出る。有限範囲の網羅は、負の値、範囲外、同時更新や実際のプログラムの正しさを保証しない。

依頼244は二人が赤・青の鍵をそれぞれ一度ずつ取得し、両方を持った後に返す有限模型。逆順ではＡが赤、Ｂが青を取得した後、互いに次の鍵を待つ状態が到達可能。同じ順序では到達可能な未完了の行き止まりはない。各鍵の排他は両方の模型で保たれる。無限の実行、公平性や実プログラムの進行性は評価しない。

依頼244の再挑戦は別の固定模型。両者が鍵を同時に返して再取得すると、鍵なしと別々の鍵を持つ状態が繰り返され、どちらも作業を終えない。Ｂが待ちＡの完了後に続ける固定順序では二人とも完了する。１段階に複数の行動をまとめ、一般の並行実装やすべての順序での公平性は扱わない。ライブロックの説明は [Oracle](https://docs.oracle.com/javase/tutorial/essential/concurrency/starvelive.html) を参考とする。

さらに精霊を一人ずつ選ぶ再挑戦の模型では、第二の鍵を取れなければ自分の鍵を返す。Ａ・Ｂがそれぞれ別の鍵を持つ状態からＡ→Ａ→Ｂ→Ｂと動かすと、両者が行動しても元の状態へ戻る。過去と現在の状態が同じとき、その間の実際の行動順を表示する。別の順序では両者が完了する。`tests/deadlock-checking.test.js` は状態の繰返し、完了、鍵の排他、記録の復元と不正な行動を検査する。80回の操作上限を持つ有限の体験であり、実装一般の進行性を証明しない。

依頼349は３ビットの鍵を手動で変異させ、鍵６の故障を観察する。故障の分岐を含む模型と省いた模型のそれぞれについて０〜７の全入力を調べ、観察した扉の結果と比べる。模型の網羅検査が示すのはその模型・範囲についての性質で、模型が対象と一致する保証はない。参考：[Lamport の仕様と実システムの違い](https://lamport.azurewebsites.net/pubs/high-level.pdf)、[LLVM の libFuzzer](https://llvm.org/docs/LibFuzzer.html)。この例は実際の自動ファザー・検査器や一般のプログラムを扱わない。
