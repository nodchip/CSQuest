# SE-Teamwork：項目別の対応状況

原典：[CS2023](https://ieeecs-media.computer.org/media/education/reports/CS2023.pdf) 印字 pp.240–241。[既存調査](se-teamwork.md)と依頼・検査を照合。状態は[追跡方法](coverage-status.md)に従う。「未照合」は未実装の証拠ではなく、「部分」は項目全体の完成を意味しない。原典の細目を分けた場合、親と子は数値上で重複計上しない。実際の開発・協働・自由な説明やコード記述の能力は固定例だけでは直接評価しない。

## 例示学習成果

| 番号 | 区分 | 要約 | 状態 | 代替と限界 |
|---|---|---|---|---|
| 1 | CS Core | 効果的なチーム内の意思疎通 | 部分 | 依頼650で３人の事情を聞き案を確認する固定例。実際の対話は未評価 |
| 2 | CS Core | 対立の原因・危険・利益を説明 | 部分 | 依頼650で異なる制約から見落としを発見する例。一般の説明は未対応 |
| 3 | CS Core | 対立解消と問題解決を進行 | 部分 | 依頼650で聞取り・制約・案・担当を選ぶ固定例。実際の進行能力は未評価 |
| 4 | CS Core | 協働開発を効果的に行う | 部分 | 依頼59は一人で固定例を操作するのみ |
| 5 | CS Core | 必要な役割と責任を提案・分担 | 部分 | 依頼650で３つの担当を選択。一般の分担は未対応 |

| 8 | CS Core | 多様性と包摂の利点を促進 | 部分 | 依頼650で当事者の参加と単一の経験を一般化しない点を扱う。現実での促進は未評価 |

依頼の前提・出典・検証と、一般化できない範囲は[既存調査](se-teamwork.md)を参照する。

依頼1066では、[Google のレビュー指針](https://google.github.io/eng-practices/review/reviewer/looking-for.html)を参考に、３つの架空の変更に対して通常条件と問題の条件を試し、問題箇所と影響を選び、修正後に両条件を再試験する。固定された３例であり、実コードのレビューや実際の協働能力を評価しない。`tests/peer-review.test.js` は修正前後の結果、旧途中記録と達成条件を検査する。

依頼1111は [Thoughtworks のペア作業の役割・課題](https://martinfowler.com/articles/on-pair-programming.html) と [Agile Alliance の群作業](https://agilealliance.org/glossary/mob-programming/) を参考に、依頼1066の３つの変更・試験結果を再利用する。２人・３人の固定例で、操作役、他の参加者の意見、修正前後の確認、役割交代と参加・疲労を扱う。仲間の発言は決められたもので、人数による品質向上や実際の協働能力は評価しない。`tests/pair-work.test.js` は２人数、各発言・操作順と復元・達成を検査する。

依頼1194は [Scrum Guide の検査と適応](https://scrumguides.org/scrum-guide.html) と [Google のレビュー指針](https://google.github.io/eng-practices/review/reviewer/) を参考に、固定の受付模型で役割を分担し、２条件の試験、問題担当、修正、再試験と別の担当による確認を行う。別担当による確認はこの依頼の約束で、Scrum 全体の要件とはしない。固定された２条件で実チーム運営や実システムの安全性は評価しない。`tests/team-project-cycle.test.js` は操作順、役割変更、修正後の再試験と履歴を検査する。
