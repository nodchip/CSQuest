依頼123では古い列「村」「件数」と新しい列「場所」「配達」を、それぞれ案内の「村名」「件数」に対応させ、同じ２行を作る。列名の変更に伴いビューの対応を更新することが必要で、任意の内部変更が自動的に隠蔽されるわけではない。実 DBMS や SQL のビュー定義は扱わない。

依頼89の追加試験は、２つの固定問い合わせについて条件と列の確認、候補数が最小の計画の選択、実行、結果の返却を順に操作する。候補数のみで計画を選ぶ簡略模型で、他の計画も同じ正しい結果を返す。実際の SQL 構文解析、書換え、統計、索引到達・行取得費用や一般の最適化器は扱わない。参考：[PostgreSQL の問い合わせ経路](https://www.postgresql.org/docs/current/query-path.html)。

依頼123の追加比較は、一意性制約による重複拒否、読み取り権限、確定前の故障時の原子的な更新、２つの増分の直列実行について、仕組みを使わない場合と正しく設定・動作する場合を比較する。４つの固定例であり、DBMS を導入しただけで自動的に安全性や全ての障害への耐性が得られるとは扱わない。参考：[PostgreSQL のトランザクション](https://www.postgresql.org/docs/current/tutorial-transactions.html)と[制約](https://www.postgresql.org/docs/current/ddl-constraints.html)。

依頼89の追加試験では、問い合わせの解析・計画と最適化・実行、バッファ管理、保存領域管理、取引管理の６つの役割を固定例で区別する。構成要素の境界・名称は実システムで異なり、実装や全構成要素を扱うものではない。[CMU のデータベース講義](https://15445.courses.cs.cmu.edu/fall2024/slides/17-twophaselocking.pdf)を参照。
