## 学習成果

| 番号 | 分類 | 要約 | 現状と限界 |
|---:|---|---|---|
| 1 | CS Core | OS における並行処理の利点と欠点 | 依頼53で仕事の待機中に別の仕事を進め、15で更新喪失の固定例。OS 全体での利点・欠点の評価は未対応 |
| 2 | CS Core | アーキテクチャ上の実行と競合状態との関係 | 依頼15で読み・更新・書込みの順序を操作。実際の命令・メモリ階層との関係は未対応 |
| 3 | CS Core | マルチプロセッサの並行処理の問題 | 依頼104で単一値のキャッシュ無効化の固定模型。一般的なマルチプロセッサの問題は未対応 |
| 4 | KA Core | OS の並行処理機構と各機構の利点 | 依頼16・178で排他と待機・通知の個別模型。機構の体系的比較は未対応 |
| 5 | KA Core | OS の同期技法と原子操作 | 依頼16の鍵による排他、178の２つのセマフォ、567の原子的な検査・設定の固定模型。実際の原子命令やセマフォの実装は未対応 |
| 6 | KA Core | コードから競合と適切な解決策を分析 | 操作の並びを比較する固定模型のみ。実コードの分析や記述は評価しない |

依頼177は毎刻１通届き、１刻に１仕事を処理する模型。固定優先度では継続到着を仮定して修理が選ばれないことを考え、優先度上昇では時刻２の同値時に修理を選ぶ。一般のワークロードに対する飢餓の不在は証明しない。

依頼178は送り手・受け手各１人、容量１の箱と空き・到着を表す２つのセマフォ。印を待つ相手に通知が直接渡る模型で、到達可能な操作順を検証。複数待機者の選択、実装や実 OS の動作は扱わない。

依頼179は同一プロセス内の２作業と独立した２プロセスの模型で、共通の記録と各自が使う札の更新を比較する。実際のスレッドのスタックは同一プロセス内の保護境界ではなく、プロセス間にも共有メモリを設けられることを明示する。

依頼567は共有の札と二人の門番の固定模型。検査と設定を別手順にすると、二人が空きを確認してから共に入れる。test-and-set では旧値の確認と使用中への設定を一操作とし、使用中なら再試行する。８手以内の全操作順で原子的な方式の同時入室がないことと、分離方式の反例を検査。再入・公平性・実機メモリ順序・性能は扱わない。参考：[Wisconsin、Locks](https://pages.cs.wisc.edu/~remzi/OSFEP/threads-locks.pdf)。

依頼568は A の仕事が戻る前に同じ処理を B で呼ぶ固定模型。共有札を使うと B が A の作業状態を上書きし、A は B を返す。呼出しごとの専用札では両方が正しく戻り、共有札でも重ならず実行すれば正しく見える。３場面と不正操作・履歴再生を検査。任意の共有資源、外部 I/O、割込みや一般の再入安全性は扱わない。参考：[MIT、Reentrant Code](https://ocw.mit.edu/ans7870/6/6.005/s16/classes/10-recursion/)。

依頼628はスレッド B の生成後、終了前の合流、終了後の合流、合流しない設定を比較。終了前の合流では A は待機して B の終了後に結果７を受け取る。終了後の合流では管理記録を保持して結果を受け取り、合流しない設定では終了時に管理記録を解放する。合流不能なスレッドへの実際の呼出しは行わず、アプリケーション自身の資源の解放やプロセス終了の扱いを区別する。[POSIX: pthread_join](https://man7.org/linux/man-pages/man3/pthread_join.3p.html)、[pthread_detach](https://man7.org/linux/man-pages/man3/pthread_detach.3.html)。

依頼629は空箱を待つ A・B に１品の到着を通知し、A が先に鍵を取って品を取り、B が後に鍵を取る固定順序。待機から戻った B が条件を再確認しなければ空箱から取ろうとし、再確認すれば鍵を解放して再び待ち、次の品で完了する。通知は品の予約ではなく、待機では鍵の解放と再取得を仮定する。一般のスケジュール、待機者の公平性、実装は未評価。[POSIX: pthread_cond_wait](https://man7.org/linux/man-pages/man3/pthread_cond_wait.3p.html)。

依頼630は２人がそれぞれ１棚を２刻更新し、共通鍵と棚ごとの鍵を比較。別棚への更新は共通鍵で４刻、棚ごとの鍵で２刻。同じ棚ならどちらも４刻。待機者への鍵の直接移譲、２台の並行実行と鍵操作費用０を仮定する。各試行の到達可能状態を列挙して鍵の所有と排他、最短時間を検査した。複数鍵の同時取得、コスト、公平性や実 OS の性能は扱わない。[Oracle: Data Locking](https://docs.oracle.com/cd/E19120-01/open.solaris/816-5137/guide-5/index.html)。

依頼631は２人・２鍵について、逆順・共通順・両鍵の一括取得を比較。逆順の行き詰まりで排他、保持待ち、非強制回収、循環待ちを確認し、共通順では循環待ち、一括取得では保持待ちを防ぐ。両予防方式について待機が生じる例も操作。全到達状態を列挙して逆順の行き詰まりを確認し、両予防方式には行き詰まりがないことをこの模型内で検査。一般の資源、実装、公平性は未評価。[Cornell: Deadlocks](https://www.cs.cornell.edu/courses/cs4410/2018sp/schedule/slides/06-deadlocks.pdf)。
