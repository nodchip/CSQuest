# NC-Reliability：送信枠と混雑（部分対応）

[CS2023 原典](https://ieeecs-media.computer.org/media/education/reports/CS2023.pdf) 印字 pp.198–199 の NC-Reliability 5 輻輳制御に関連する固定模型。旧依頼423 `congestion-aimd.js` は２人の伝令と共有容量の加法増加・乗法減少を扱うため、重複を新しい範囲として二重計上しない。現行の塔の窓・再送模型は信頼性を扱うが、共有路の輻輳による送信枠の調整を扱わない。

送信者１人、１回の通行能力２通、送信枠の数だけ必ず送ると仮定。２通以下は全て届き、３通以上はこの例では全て届かず混雑の知らせが即時に返る。成功時に枠＋１、混雑時は２で割って切り捨て、最低１とする。この模型では枠１・２・３・１、届く通数１・２・０・１となる。[RFC 5681](https://www.rfc-editor.org/rfc/rfc5681) の輻輳ウィンドウや輻輳時の調整を背景にした独自の整数模型であり TCP の挙動を再現しない。

実 TCP の ACK・RTT・輻輳ウィンドウの単位、スロースタート、再送・確認、損失の原因や一部到達、遅延・複数送信者の公平性・一般の性能を扱わない。容量超過ですべて失われることは現実全体の主張ではなく、再送の実施も未評価。NC-Reliability 全体は未完成。

実装担当とは別の `review_candidate` が原典・RFC と独自の整数模型、固定例の数値、画面の前提と実 TCP との差、誤答・不正履歴、分類と開放、旧記録の既定値を確認した。関連６テストも成功した。実ネットワークや TCP 実装を検証したものではなく、レビュー担当自身はブラウザを操作していない。

`scripts/endgame-congestion-bridge.playwright.js` は集いと４地域の達成状態を用意した検証用記録から、213・390・1200 px 幅で分類経由の到達、キーボード操作、誤答案内、途中保存・再開、段階開放と達成後の再開を確認した。新規開始からこの依頼への通し操作、実際のスクリーンリーダー音声や利用者による面白さの評価は未確認。
