台帳は既存の例と不足を記録するもので、原典全体の網羅・教材の正確性・大学水準の深さを証明しない。各模型の前提と個別検証は[通信分野の記録](pdc-communication.md)を参照。

依頼993は [MIT の待ち行列の資料](https://web.mit.edu/dimitrib/www/Queueing_Data_Nets.pdf) を参照し、ポアソン到着・独立な指数処理時間・先着順・１受付・無限バッファを仮定する M/M/1 を扱う。処理率４、到着率１〜５を比較し、定常条件、処理中を含む系内平均、待ち行列だけの平均と Little の法則を区別する。有限時間の実測、有限バッファ、一般の到着・処理分布や複数受付には一般化しない。`tests/queue-model.test.js` は３つの定常値、２つの非定常条件、正答・保存・達成を検査する。

依頼994は固定の４通の到着と処理を６区間進め、各区間の系内通数の合計９通・刻を、完了済みの滞在時間７刻と観測終了時の未完了の経過時間２刻に分ける。有限区間で完了分だけを用いる場合の境界を示す例であり、定常状態の証明、M/M/1 の乱数実験や実環境の観測ではない。`tests/queue-observation.test.js` で６区間の通数、到着・完了・未完了、時間の保存関係と途中記録・達成を検査する。

依頼995では到着率３・サービス率４の１受付について、異なる二つの固定された種と観測時間10・1000の４条件を比較する。到着間隔と処理時間は別の xorshift32 疑似乱数列から逆変換で指数分布の標本を生成し、空の系から事象を追跡する。[Utah のシミュレーション講義](https://www.math.utah.edu/~ethier/5040-sim-lectures1-5.pdf) と [MIT の待ち行列資料](https://web.mit.edu/dimitrib/www/Queueing_Data_Nets.pdf) を参照。表示の丸め、初期過渡、未完了を明示し、有限の４観測を実機測定や精度保証と扱わない。`tests/queue-simulation.test.js` は固定履歴との照合、種の再現・履歴の先頭、到着の保存、観測面積と完了・未完了時間の一致、保存と達成を検査する。

依頼996は受信処理中の１通と受信待ち０・１通を区別し、固定された５通の発生と各刻の受付を追う。満員時には送信側の無制限の保留で先頭を再試行するか、受付に失敗した手紙を破棄するかを比較する。破棄はこの模型で選んだ判断であり、API の失敗が常に自動破棄を意味するわけではない。[Java BlockingQueue の仕様](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/util/concurrent/BlockingQueue.html) は待機する put と失敗を返す offer の違いを示す。実 API、ネットワーク障害、送信側の保留容量や一般の流量制御は評価しない。`tests/channel-pressure.test.js` で４条件の各刻に発生済み手紙が重複なく保存・処理・破棄されること、履歴、途中記録と達成を検査する。

依頼997では２通信路の読み取り可能通知、通知後に別の読み手が先に取った場合の非ブロッキング読取りと再試行、非同期操作の保留・別作業・完了通知を固定した３場面で比較する。[Linux select の説明](https://man7.org/linux/man-pages/man2/select.2.html) と [Microsoft の I/O Completion Ports](https://learn.microsoft.com/en-us/windows/win32/fileio/i-o-completion-ports) を参照。操作順と所要刻は模型の条件であり、実際の API に先行確認を必須とする主張ではない。即時完了、EOF、取消し、エラー、実 API・一般のスケジューリングは評価しない。`tests/io-notifications.test.js` は両読取り順、競合・再試行、完了前の取得拒否、履歴復元と達成を検査する。

依頼998は非公開の記録を送る固定用途で、受動的盗聴、鍵差替えを伴う改変、王城のなりすまし、役割のない者の閲覧を別々に比較する。暗号化・改変検出が理想どおり動き、身元確認では正しい鍵が事前に安全に登録されると仮定する。鍵の管理、実装、端末侵害や通信量の漏えいを評価せず、すべての攻撃に対する安全性を証明しない。[NIST の認証](https://csrc.nist.gov/glossary/term/authentication) と [認可](https://csrc.nist.gov/glossary/term/authorization) を参照。`tests/message-protection.test.js` で４つの守りの全16組合せと４場面、保存と達成を検査する。

依頼999は２種類の印を最大８個とする独自の小さな形式で、方式と本文長を１バイトずつ記し、非圧縮と連長符号化のサイズを比較する。受信側は方式、本文長、組、印、展開後の上限を確認してから復元する。形式の一致は本人確認や改変検出を意味せず、実際の暗号は扱わない。[MITRE の長さ不一致](https://cwe.mitre.org/data/definitions/130.html) と [数量の検証](https://cwe.mitre.org/data/definitions/1284.html) を参照。`tests/message-frame.test.js` は長さ０〜８の全511通りの印列と両方式の往復、不正な長さ・組・印・展開上限、保存・達成を検査する。実プロトコル、実際の圧縮形式と安全性は評価しない。

依頼1000は二人が各１回送受信する有限模型で、待ち合わせ式と各方向１通の箱式、二人目の送受信順を比較する。各状態から可能な遷移を列挙し、同一状態をまとめて到達可能状態と完了・デッドロックの経路を求める。[Carnegie Mellon の同期送受信の資料](https://www.cs.cmu.edu/afs/cs/academic/class/15418-s21/www/lectures/rec_05.pdf) を参照。模型に故障・無限の再送・公平性はなく、CSP 言語、実 API や一般の安全性を証明しない。`tests/channel-reachability.test.js` は４条件の状態数・終端と経路、箱容量、途中記録・達成を検査する。

依頼1001は初期値０の原子的な品物と旗について、書き手の品物42・旗１、読み手の旗・品物の順を固定する。旗の release 書込みを acquire 読取りが直接読んだ場合と、初期値を読んだ場合、旗が relaxed の場合を比較する。両変数は原子的で、品物の操作は relaxed、他の書込みはない。[C++ working draft の原子操作順序](https://eel.is/c++draft/atomics.order) と [競合の規則](https://eel.is/c++draft/intro.races) を参照。`tests/release-acquire.test.js` は８組の判定、逐次一貫な順序の全列挙、保存と達成を検査する。固定例の許される結果であり、release sequence 全般、非原子的データ、実機での観測や一般の C++ 実装を評価しない。

依頼1002では1001と同じ２人の操作順で、旗は原子的、品物は原子的または非原子的とする。読み手は旗０でも品物を必ず読み、他の同期や書込みはないと仮定する。release の１を acquire が直接読んだときは品物の書込みが読取りより前に順序付けられ、それ以外で非原子的な品物を使うとデータ競合による未定義動作となる。原子的な品物の場合は競合ではないが同期の有無で許される値が異なる。[C++ working draft の競合の規則](https://eel.is/c++draft/intro.races) と [原子操作順序](https://eel.is/c++draft/atomics.order) を参照。`tests/publication-race.test.js` で８条件と1001の原子的な判定、保存・達成を検査する。固定された無条件読取りの例であり、一般の C++ プログラム、他の同期、実機の動作は評価しない。

依頼816は読み手が目印を公表して先頭を再確認する固定例で、回収済みの参照や回収の延期を扱う。依頼1003は共有欄が一つの所有権を持つ模型で、生の位置の読取り後の回収、同じ鍵による保護、一体の所有権取得が削除より前・後となる４順序を比べる。[C++ working draft の atomic smart pointer](https://eel.is/c++draft/util.smartptr.atomic) と [IBM Research の hazard pointers](https://research.ibm.com/publications/hazard-pointers-safe-memory-reclamation-for-lock-free-objects) を参照。標準では所有数の減少・削除は原子的更新の一部とは限らず、この模型の回収完了時刻は単純化している。実装、ロックフリー性、循環参照や回収の一般的な証明は評価しない。`tests/hazard-reclaim.test.js` と `tests/shared-ownership.test.js` で固定履歴、回収・所有状態、復元と達成を検査する。

依頼1004は通常の RDMA 書込みの固定模型で、接続・送信元登録を済ませ、遠隔の登録範囲・鍵・書込み権限を変えて結果を比較する。成功した送信側の完了確認と受信側アプリへの別の通知・処理を区別し、伝言を受信側が記録に写す模型と比較する。[NVIDIA の RDMA プログラミング資料](https://docs.nvidia.com/rdma-aware-networks-programming-user-manual-1-7.pdf) は通常の write と通知を伴う write with immediate を区別する。実際の API、受信側への通知方式、順序、障害、整合性、メモリー登録の実装や性能は評価しない。`tests/rdma-transfer.test.js` で伝言・書込み、鍵・範囲・権限の失敗、途中記録と達成を検査する。

依頼1005は一つの値と一つの写しに限定し、無効化が遅れる例、書込み完了前に無効化を待つ例、RDMA で更新された元の値とアプリが別に管理する写しを比較する。[UC Berkeley の講義](https://people.eecs.berkeley.edu/~kubitron/courses/cs252-S12/lectures/lec20-sharedmemory3.pdf) は無効化と書込み完了の関係を説明する。[USENIX の論文](https://www.usenix.org/conference/osdi-94/message-driven-relaxed-consistency-software-distributed-shared-memory) はソフトウェア DSM の緩和された整合性を扱う。例は特定の順序に限られ、一般的な線形化可能性や実機のキャッシュ整合性を証明しない。`tests/dsm-cache.test.js` で値と完了時点、途中記録を検査する。

依頼1006は Raft の５塔、任期２の記録Ｘと現在の任期４の記録Ｙについて、代表の知る保存応答と通信の分断・復旧を比較する。[Raft 論文](https://raft.github.io/raft.pdf) §5.3–5.4 の現在任期の記録を過半数で直接確定し、それ以前を間接確定する規則を参照。Ｘが過半数にあるだけでは、この代表は票数だけから確定できない。以前にＸが既に確定済みだったかは不明という設定で、未確定だと断定しない。選挙、RPC の詳細、ログ修復、再起動、全実行や安全性の証明は対象外。`tests/raft-log.test.js` で３つの復旧先、早すぎる確定、通信不能、保存と達成を検査する。
