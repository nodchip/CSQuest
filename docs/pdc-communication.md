出典: [CS2023](https://ieeecs-media.computer.org/media/education/reports/CS2023.pdf) 印字 pp.220–222。ゲーム内の操作は実際の並列プログラムの作成や性能測定を直接評価しない。

依頼129は単一の送り手が赤・青を順に送り、受け手が順に受け取る。容量０は相手が受信するまで送信を保留し、容量１は１通を格納できる。満杯で２通目を送ると待ち、先の１通を受信すると待機中の伝言が箱に入り送信が終わる。空の受信は待機状態を保存せず通知する簡略モデルであり、実装、時間、障害や複数主体は扱わない。

依頼131は容量０の双方向通信で、各送信・受信は相手と出会うまで完了しない。両者が先に送る手順は互いに送信待ちとなり、片方が先に受け取る手順は両方の伝言を交換できる。２主体・２通の模型であり、他の API や任意の通信手順に一般化しない。

依頼505は係Ａ・Ｂが別の値を２回ずつ書く模型。２値が同じ行なら交互 ABAB で持ち替え３回、まとめた AABB で１回、行を分けた交互では０回。最初の取得は持ち替えに含めない。全６種の合法な作業順を検証した。実機のプロトコルや性能を再現・測定せず、まとめて書く手順の適用可能性や配置のメモリ費用も扱わない。[Oracle の偽共有の説明](https://docs.oracle.com/cd/E37069_01/html/E37081/aewcy.html)を参照。

依頼508は初期 x=y=0 でＡが x=1 の後に y、Ｂが y=1 の後に x を読む。即時反映で各精霊の順番を保つ６通りの結果は (0,1)、(1,0)、(1,1) のみ。書込みを各精霊の一時置き場に保持し、両者が読んだ後に反映すると (0,0) が可能になる。これは小さな操作模型で、実言語のデータ競合、一般のハードウェアモデル、同期やプログラムの安全性は評価しない。[Lamport の逐次一貫性](https://lamport.azurewebsites.net/pubs/multi.pdf)、[Cambridge の x86-TSO](https://www.cl.cam.ac.uk/techreports/UCAM-CL-TR-745.html)を参照。
