# NC-Applications：項目別の対応状況

原典：[CS2023](https://ieeecs-media.computer.org/media/education/reports/CS2023.pdf) 印字 p.199。[既存の調査](nc-applications.md)と依頼・テストを照合。状態は[追跡方法](coverage-status.md)に従う。すべて CS Core。固定模型は実通信や実際のソケットアプリの開発能力を直接評価しない。

## トピック

| 番号 | 要約 | 状態 | 対応例と限界 |
|---|---|---|---|
| 1 | DNS・URI などの名前と住所 | 部分 | 421で DNS の名前解決・期限と権威側の更新、669で相対参照・検索条件・フラグメントを操作。一般の名前付けや実通信は未評価。 |
| 2 | クライアント・サーバー、P2P、クラウド、エッジ等 | 部分 | 62で端末と受付、667で中央書庫と既知の仲間からの受信・複製を比較。クラウド、エッジ等の一般の構成は未評価。 |
| 3 | 遅延・帯域・損失耐性など用途ごとの要求 | 部分 | 668で完全性・期限と、荷物の大きさ・伝送速度・伝播時間を固定例で比較。一般の要求分析と実通信は未評価。 |
| 4 | HTTP などアプリケーション層プロトコル | 部分 | 62で POST の再送、670で条件付き GET の固定例を操作。HTTP 全体や実通信は未評価。 |
| 5 | TCP・UDP・ソケット API との相互作用 | 部分 | 424で接続開始、668で順序付きバイト列とデータグラムの損失時を操作。実ソケット API や実通信は未評価。 |

## 例示学習成果

| 番号 | 要約 | 状態 | 対応例と限界 |
|---|---|---|---|
| 1 | 名前・住所・資源の位置の原則を定義 | 部分 | 421・669で DNS と URI の固定例を操作。一般の定義と自由な説明は未評価。 |
| 2 | ネットワークアプリの要求を分析 | 部分 | 668で損失・期限と、荷物の大きさによる到着時間を比較。一般の分析や実測は未評価。 |
| 3 | アプリケーション層プロトコルの詳細を説明 | 部分 | 62・670で POST 再送と条件付き GET を操作。HTTP 全体や自由な説明は未評価。 |
| 4 | クライアント・サーバーのソケットアプリを実装 | 部分 | 62で端末・受付間の再送を操作する代替体験。実ソケットアプリの設計・記述・実行は直接評価しない。 |

`tests/transport-needs.test.js`、`tests/link-choice.test.js` 等は固定模型の一部を検査する。前提・出典・限界は[既存の調査](nc-applications.md)を参照。依頼668の到着時間は待機・処理・損失がない１通信路を仮定し、実際の期限を保証しない。

依頼421の追加例は、時刻０にキャッシュを作り、権威側の住所が時刻１に変わると仮定する。期限を２・４・６刻から選び、５時刻の問い合わせをそれぞれ独立に比較する。例えば期限４では通知がないため時刻１・３でも変更前の住所を返し、時刻４以後の問い合わせでは権威側を再確認する。`tests/dns-resolution.test.js` は15条件と旧記録を検査する。実際の DNS の全動作や反映時間は保証しない。参考：[RFC 1034](https://www.rfc-editor.org/rfc/rfc1034)。
