# FPL-Design: プログラミング言語の設計原則

出典：[CS2023 印字 pp.146–147](https://ieeecs-media.computer.org/media/education/reports/CS2023.pdf)。すべて Non-core。架空の固定例での比較は、実言語の一般的な評価能力を示さない。

| トピック | 対応と不足 |
|---|---|
| 1a 単純さ | 依頼355で例外規則を比較。言語全体の単純さの評価は未対応 |
| 1b セキュリティ | 未対応 |
| 1c–d 翻訳の速さと生成コードの効率 | 未対応 |
| 1e 直交性 | 依頼355で２種類の値と２つの場面の組み合わせを比較。一般の構成要素や意味の一貫性は未対応 |
| 1f 可読性 | 未対応 |
| 1g 完全性 | 未対応 |
| 1h 実装戦略 | 依頼355で組み合わせ増加による複雑さに言及。実際の実装戦略は未対応 |
| 2 特定領域・問題に合う言語設計 | 未対応 |
| 3 言語間の相互運用性 | 未対応 |
| 4 移植性 | 未対応 |
| 5 言語の形式的記述 | 依頼281で固定式の操作的意味論。実際の言語の記述は未対応 |
| 6 グリーンコンピューティングの原則 | 未対応 |

| 例示学習成果 | 対応と不足 |
|---|---|
| 1 良い言語設計を理解し、実在言語の評価に適用 | 依頼355は２つの架空の規則の一部分を比較。実言語全体の評価は未対応 |

依頼355の古い規則は数と数の列の保存、および数の返却を許すが、列の返却を許さない。そろえた規則は４通りを許す。直交性の考え方と、組み合わせの増加が複雑さを増す可能性については [NYU の言語設計講義](https://cs.nyu.edu/~mishra/COURSES/08.ProgLang/l4%209-29) を参考にした。型の一致を前提とした架空の例であり、任意の型の組み合わせが常に正しいという主張ではない。
