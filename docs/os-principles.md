# OS-Principles の対応状況

出典: [CS2023, OS-Principles](https://ieeecs-media.computer.org/media/education/reports/CS2023.pdf) 印字 p. 207。以下は原典を要約した作業用一覧。依頼54は保護と呼び出しの簡略例で、知識単位全体の修了を示さない。

## トピック

| 番号 | 分類 | 要約 | 現状 |
|---:|---|---|---|
| 1 | CS Core | OS の設計方式（モノリシック、階層型、マイクロカーネルなど） | 依頼381でカーネル内サービスと利用者プロセスに分けたサービスの固定模型を比較。階層型や実際の OS は未対応 |
| 2 | CS Core | 抽象化、プロセス、資源 | プロセス状態と装置の保護の固定例。抽象化全般は未対応 |
| 3 | CS Core | システムコールと API | 依頼54・384で OS への依頼とファイル操作の引数・返り値の固定例。実際の API 呼出しは未対応 |
| 4 | CS Core | ハードウェアと OS の関係の発展 | 依頼672で協調的実行と保護されたタイマー割込みの固定模型を比較。歴史や他のハードウェア支援は未対応 |
| 5 | CS Core | 命令・機能の制限による資源保護 | 依頼54で保護された装置への直接操作と許可の例。具体的な命令や他の資源は未対応 |
| 6 | CS Core | ハードウェア割込みと処理ルーチン | 依頼105で装置の完了通知・処理・復帰の固定例。実際のハードウェアや優先順位は未対応 |
| 7 | CS Core | 利用者・カーネルモード、システムコールによる移行 | 依頼54で利用者からカーネルへの移行、許可の確認と復帰を操作 |
| 8 | CS Core | システムコールの呼出し、モード・コンテキスト切替えと復帰 | モードの変化と復帰を例示。実際の呼出し機構やコンテキスト切替えは未対応 |
| 9 | CS Core | 切替えやキャッシュへの影響による性能費用 | 依頼381で模型のモード変更回数を比較。実時間、キャッシュへの影響や一般の性能評価は未対応 |

| 番号 | 分類 | 要約 | 現状と限界 |
|---:|---|---|---|
| 1 | CS Core | OS の設計方式が堅牢性・保守性に与える影響 | 依頼381でファイル担当の故障影響を比較。一般の設計・保守性評価は未対応 |
| 2 | CS Core | システムコールを目的別に分類 | 依頼384でファイル操作、386でプロセス生成・実行・終了確認の固定例。一般の分類は未対応 |
| 3 | CS Core | システムコールの引数やモード変更を理解 | 依頼54でモード変更、依頼384でファイル番号・読取量・返り値の固定例。実際の呼出し機構は未対応 |
| 4 | CS Core | アプリケーション層とシステムコールが必要な機能を区別 | 保護された装置への直接操作と依頼を比較。一般的な分類は未対応 |
| 5 | CS Core | OS の分離、保護、スループットの技術を他の場面に応用 | 保護の限定例のみ。一般的な応用は未対応 |
| 6 | CS Core | モードの分離が安全性・性能に与える影響 | 依頼54で直接操作の制限、依頼381で故障影響とモード変更回数の固定例。実性能や一般の安全性は未対応 |
| 7 | CS Core | 多重プログラミングにおける割込みの利点と欠点 | 依頼105で装置待ち、672で制御を得て別作業へ移る固定模型。実際の費用・欠点の定量評価は未対応 |
| 8 | CS Core | OS を介した攻撃経路と防御を分析 | 依頼671で受付の権限を介した他人の記録へのアクセスと照合・権限制限を比較。一般の攻撃分析は未対応 |

実際の OS や装置を動かすものではない。直接操作時の例外処理や、カーネルへの侵入・復帰に必要な機械語レベルの動作は省略している。

依頼381は一体型ではファイル・装置担当をカーネル内、分離型では別の利用者プロセスに置く固定模型。通常の読出しのモード変更は前者２・後者８回で、ファイル担当の故障時は前者で OS 停止、後者で担当のみ停止と仮定する。分離には保護・復旧の仕組みが必要であり、データの整合性や実速度を保証しない。モノリシック・マイクロカーネルの実装は多様で、この回数を一般化しない。[参考：Carnegie Mellon の Mach 多サーバ](https://www.cs.cmu.edu/afs/cs/project/mach/public/www/mach_us/mach_us_whatis.html)

依頼384は読み取り可能・書き込み不可の既存ファイル ABC を、番号３で２バイトずつ読む固定模型。順に AB の２バイト、C の１バイト、終端の０が返る。未使用の番号４と閉じた番号３では EBADF、書込用に開く要求は EACCES とする。閉じた後も内容は残り、開き直すと先頭から読む。番号と権限は仮定で、実際のシステムコールの実行や全エラーは扱わない。[read(2)](https://man7.org/linux/man-pages/man2/read.2.html)、[open(2)](https://man7.org/linux/man-pages/man2/open.2.html)。

依頼671は認証された A・B、各自の記録、両者が依頼できる受付を仮定する。直接読みは本人の OS 権限を、受付経由は受付の OS 権限を使う。照合のない広い受付では他人の記録が渡り、依頼者と対象の照合で拒否できる。受付を A の記録のみに制限した場合、B へのアクセスは止まるが B から A の記録への無照合依頼は通り、B 自身の正当な依頼も失敗する。全24条件を検査。実 OS や認証・一般の権限モデルは扱わない。[OWASP: Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

依頼672は A が自発的に譲らず、他の割込み・例外もない３刻の模型。時計なし、A が時計を止められる場合、利用者が止められない時計の場合を比較する。最後は２刻目に割込みが起き、OS が B を選ぶと３刻目に１刻の仕事が終わる。時計だけで公平性や期限を保証するとはしない。実機の割込み、歴史やコンテキスト保存は未対応。[OSTEP: Limited Direct Execution](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-mechanisms.pdf)。
